RESOLVE: a proposed general investigation and planning layer

Research proposal • 11 October 2026 • Not implemented or benchmarked

Proposal: build RESOLVE as a general investigation and planning layer, with code-managed state and model-generated, testable proposals. Its competence comes from the combination of model reasoning, memory, search, domain tools, observation and validation. The executor determines the available actions and observations; allowing more actions alone does not create intelligence.

This is a research design, not an implemented capability or an AGI claim. It is intended to test whether unfamiliar objectives can be solved without a developer writing each solution method. It does not reduce the goal to the downloaded POC’s two lab actions.

What could count as general intelligence

A successful autonomous security system would demonstrate important domain competence. An AGI claim additionally needs broad transfer, learning and reliable performance across substantially different domains. Levels of AGI distinguishes performance, generality and autonomy. My proposal is to evaluate the complete READ + RESOLVE + model + memory + executor system against a declared capability profile; no individual layer or dial setting receives an AGI label by construction.

A permissive executor is neither sufficient nor always necessary: missing observations, weak hypotheses, incorrect domain models and bad verification can still prevent success. Conversely, a restricted executor can reveal substantial planning competence through correct plans and explicit explanations of blocked obligations.

Ownership and the two paths
---------------------------

Kobra owns the language and program-authoring semantics, as already recorded in
architecture-decisions.rst. Gorgon owns concrete tools and downstream execution.
Their boundary remains versioned data, not imports of each other's internals.

New natural-language work:

    READ meaning and evidence
      -> RESOLVE objective, hypotheses and decomposition
      -> Meduza program construction and validation
      -> ROUTE approval of the proposed handoff
      -> executor, with per-call checks
      -> observations/verdicts returned as data to RESOLVE

Existing saved program:

    load program and pinned dependencies
      -> validate and ROUTE under current grants
      -> execute

Executing a saved program does not reinterpret its source as a new English
request. Reusing it still requires current applicability and execution checks.

RESOLVE's internal graph represents unknowns, alternatives and dependencies.
Meduza represents a selected executable procedure or a supported goal/check.
They have different jobs: the graph is not a second runtime language, and a
Meduza program cannot be used as a replacement for all unresolved reasoning.
Answers, attributed statements, ASK and unsupported results need not be programs.

How RESOLVE uses it
------------------

1. READ supplies supported meaning, roles, qualifiers and grounded references.
   Missing user intent stays ASK; an execution dial cannot supply that meaning.
2. RESOLVE identifies the next evidence or goal obligation and looks for an
   applicable method using manifests and recorded evidence.
3. A deterministic method constructs the program where possible. For unfamiliar
   work, a model proposes a decomposition or selects a bounded method; code
   constructs the artifact and keeps source/goal links.
4. Class selection is a separate bounded decision over the public methods of
   the relevant receiver. Do not put every class implementation into a global
   authoring prompt. Necessary constraints remain enforced by the harness.
5. Validate types, bindings, scalar/set cardinality, intent, effects, dependencies
   and predicates before handing the artifact to ROUTE. Unsupported meanings
   must not be silently erased to fit the existing Meduza subset.
6. The executor enforces each underlying call, including calls inside methods,
   packages and recovery blocks. A reusable method is not a trusted region.
7. Return observations and verdicts with program/action identity, artifact and
   world revisions, timestamps and provenance. RESOLVE updates its evidence graph
   and either advances, derives a supported correction or considers another plan.

FETCH is not omniscient truth. ENSURE proves only what its predicate and evidence
actually establish. ACHIEVE is neither unlimited authorization nor a general
solver. Historical tool reliability, semantic confidence and achieved-objective
verification remain separate quantities; none is a model self-confidence score.

Compilation and classes
-----------------------

Prefer reusing or extracting a reviewed language compiler over inventing a second
DSL. A minimal adapter preserves existing language behavior with less initial
migration risk; extracting language-only modules into Kobra better matches final
ownership but requires dependency separation and conformance tests. Begin with
fixtures and a data contract, then choose the migration slice based on the actual
imports. Do not move the complete engine and lab manifest into Kobra wholesale.

The compiler must refuse unsupported graph nodes and report which obligation it
cannot express. Not every surface construct lowers into a tiny core: FETCH,
conditionals, predicate combinators and set behavior must retain their semantics.

A reusable class method should carry a public signature, version, preconditions,
effects, postcondition, evidence requirements, capability dependencies and test
history. Preserve the earlier class-file proposal's auditable expansion: pin and
expose the body before execution, or require an equivalent recursively checked
artifact boundary. Tested once does not mean correct in every new context.

All cockpit limits continue to apply. Planning/complexity bound decomposition;
Reins bounds model choices; Intent bounds permitted goal changes; Learning governs
method promotion; scope, effects and budgets apply to every expanded operation.
Persistence governs saved/triggered execution. No dial turns a failed ENSURE into
a successful verdict or makes an unknown method executable.

The proposed loop

READ meaning → Goal contract → Evidence and hypothesis graph → Next research obligation → Candidate plan or experiment → Validation → ROUTE → Executor observation → Evidence update → Replan or conclude

There are two work paths. For a known, applicable method, code advances the method and calls tools without repeatedly asking the model what to do. For an unresolved reasoning obligation, the model gets a bounded packet and proposes an experiment, decomposition, explanation or method candidate. New outcomes may reopen earlier decisions.

  1. Compile the objective. Preserve intent, scope, exclusions and meaning. Define observable success obligations; unknown success criteria stay explicit. Questions request supported answers; assertions update attributed claims; neither becomes an action automatically.
  2. Load relevant state. Retrieve evidence and skill candidates with dependencies, freshness and contradictions. Keep user constraints and unresolved alternatives in every necessary projection.
  3. Select an obligation. Choose a missing fact, competing hypothesis, unproven dependency or unfinished goal. Prefer useful discriminating observations over repeating a narrative.
  4. Generate alternatives. Reuse applicable methods, search formal subproblems, or request model proposals. An alternative states expected observations, assumptions, cost bounds and what would refute it.
  5. Validate and dispatch one frontier. Code checks references, capability schemas, constraints and budgets. Domain tests or simulators check what they can. ROUTE/executor enforce current authority.
  6. Update and revise. Append observations, invalidate dependent conclusions, retain completed effects, and replace only future work. If the domain model fails, revisit it rather than forcing the original plan.
  7. Finish with a typed result. Report achieved, partial, inconclusive, ASK, blocked or unsupported, with evidence for each completed obligation. No unobserved success inferred from a successful API call.

The representation must allow unfamiliar work

Use an extensible typed graph, not a fixed list of task names. Core node types: goal, question, hypothesis, claim, observation, experiment, capability call, artifact, constraint, verification obligation and learned method. Edges include requires, supports, contradicts, tests, produces, derived-from and supersedes. Plan dependencies are partial-order relationships; source-order conjunction alone does not force execution order.

The core schema can remain finite while values, domain types, tasks and evidence grow. Capability manifests describe input/output types, preconditions, possible effects, observation reliability, cost, idempotency and required grants. Domain packs provide reusable operators and checkers, not the hidden solution for every evaluation task. Unknown operators remain proposals until an executor actually supplies a validated implementation.

Hypotheses may contain model-authored text and structured predictions. This is necessary for novel reasoning; requiring every idea to come from a predefined answer list would cap the experiment at recombination. The code still constructs envelopes, checks references and preserves uncertainty. Formal proofs are possible only in formalized subsets; passing tests elsewhere is empirical evidence, not universal correctness.

Semantic knowledge and procedures should have distinct namespaces even if stored in one database. Runtime skill code lives with the executor; Kobra sees manifests and method descriptions through the data boundary. The POC’s dictionary Archive and simulator snapshots do not replace existing Kobra stores.

Context selection is code-managed but not magically complete. Retrieval must record what it fetched, the versions used, missing dependencies and truncation/overflow. Constraints cannot be dropped to fit a prompt. A failed search means missing evidence, not evidence of absence. Ask for another bounded retrieval job when the current packet is insufficient.

Model judgment and external confidence

Model roles are hypothesis generation, novel decomposition, relevance judgments, experiment proposals, synthesis and candidate skill construction. Code owns identifiers, schema assembly, state transitions, deterministic checks, dependency tracking, budgets, provenance and tool dispatch. A second model can critique a proposal, but agreement between related models is not independent evidence.

Represent truth/evidence status separately from confidence: supported, refuted, unknown and conflicting; also record freshness and assumption status. Model self-confidence never grants authority or labels a finding verified. External cohort calibration describes observed reliability on comparable tasks; it is not automatically a probability for a novel hypothesis or an entire campaign. Out-of-distribution cases retain unknown calibration.

Select experiments using expected usefulness, cost and uncertainty reduction. Where no calibrated probability model exists, use explicit ordinal rankings and assumptions rather than invented information-gain numbers. A useful negative result prunes a hypothesis and counts as progress. Repeated failed actions without new evidence consume a retry budget and trigger a strategy change or stop.

Four different kinds of unresolved work

ConditionResponse
Meaning or intended referent is ambiguousASK through the existing READ/context path; do not guess from model preference.
Meaning is clear but a world fact is missingPropose an observation, subject to capability and scope checks.
A scientific/technical claim is uncertainMaintain competing hypotheses and propose a discriminating test.

This distinction allows substantial autonomy without treating user ambiguity as permission to invent intent. Missing production calibration also remains an acceptance issue distinct from these linguistic and research questions.

Example: authorized automated assessment

Objective: assess a specified isolated lab and produce evidence-backed findings within the granted scope. READ supplies the objective, target set, exclusions and intended outputs. RESOLVE identifies missing observations and the conditions needed for a defensible finding.

The executor may expose inventory, configuration inspection, controlled validation and report-artifact capabilities. RESOLVE chooses among supported assessment hypotheses, requests observations, adjusts the remaining work when configuration differs from expectations, and stops a line of inquiry when evidence refutes it. Every finding points to the actual observation, target identity, environment version and validation result. Unexamined areas remain coverage gaps rather than a blanket “secure” verdict.

The novelty test is whether it handles a held-out configuration or misleading initial observation without a developer adding the exact scenario as a new method. This example describes capability requirements and evidence flow; it does not prescribe exploitation steps or make external targets part of the authorized scope.

Example: local binary/decompilation research

Objective: investigate whether an unfamiliar local program violates a supplied correctness or security property. Input artifacts have hashes and versions; decompiled output is recorded as an imperfect analysis artifact, not source truth.

RESOLVE identifies relevant program regions from executor-supplied evidence, proposes competing behavioral explanations, and chooses observations that distinguish them. Controlled local execution and analysis tools produce artifacts. A hypothesis becomes a finding only when supported by a reproducible result and an explanation consistent with the evidence. If a suspected flaw is not reproduced, the result stays inconclusive or refuted.

Crashing is not automatically exploitability, a vulnerability is not automatically new, and novelty cannot be inferred from the model failing to recall a disclosure. Known-vulnerability reproduction, hidden-defect discovery and independently confirmed novel discovery need separate scores. The same mechanism should also work on ordinary correctness defects; that gives a transfer test beyond security labels.

Verification must track the actual event

The downloaded POC’s repeated-event failure is a useful acceptance test for this design. A first successful event must not verify a second event whose telemetry is missing. Evidence keys need the relevant objective, action/event identity, artifact or environment version and observation time. Refreshing a world snapshot is insufficient unless dependent claims are invalidated too.

Keep action completion, observed effect and achieved objective separate. Use deterministic checks where they are sound, empirical tests where they are meaningful, and explicit human review where the claim exceeds available validation. The agent cannot rewrite hidden success criteria or grade itself by a test it weakened. Unknown mutation outcomes require reconciliation before another attempt; persistent recovery replays action identities rather than reissuing work blindly.

The next POC must test the actual hypothesis

Hypothesis: with the same model, executor and budgets, explicit evidence memory plus hypothesis-driven decomposition and replanning improves verified completion on unfamiliar tasks beyond both a flat agent and fixed methods.

Start with a proposed screening suite of 24 held-out tasks: four each in isolated security assessment, local program analysis, unfamiliar code repair, service diagnosis, data investigation and constrained operational planning. Use independently authored tasks and hidden evaluation artifacts. Three repetitions under three comparison arms gives 216 trajectories. This is a practical screening design, not enough evidence to certify AGI or tiny failure rates. Use separate development tasks; once a held-out failure is used for tuning, its next run is regression evidence.

Implementation order and unresolved research risks

  1. Contract and evidence kernel. Map actual READ distillation into objective and evidence records, with no loss of qualifiers or grounding. Add event-specific verification and replayable transitions.
  2. One genuine reasoning cycle. On unseen tasks, require a model-generated hypothesis and experiment; compare an expected observation with the actual result. Measure refutation and recovery as well as success.
  3. Alternative decompositions. Use a finite frontier and formal checking where applicable. Test changed assumptions, unavailable capabilities and contradictory observations.
  4. Transfer and evaluated skill reuse. Hold the core fixed while adding a domain through capability manifests. Evaluate whether reusable methods help new tasks without solution leakage.
  5. Longer runs and bounded workers. Add persistence, resumability and delegation only when shorter serial runs demonstrate a benefit. Keep a combined budget and independent evidence checks.
  6. Learning and broader autonomy. Promote candidate methods only after independent regression/transfer checks; assess the upper dial levels separately rather than turning them all on.

Unresolved risks include insufficient model reasoning, inaccurate domain models, incomplete retrieval, correlated critics, weak success predicates, tool errors, open-world uncertainty and compounding mistakes over long horizons. More rules can improve known checks; they cannot guarantee generation of the missing insight. A small model may gain from this structure, but no evidence here establishes parity with a stronger model. Test that as a separate ablation with named weights and identical budgets.

The research decision is to pursue a general, evidence-driven deliberation mechanism and test whether it supplies novel useful work. Calling it AGI remains conditional on measured breadth, competence and transfer of the complete system.
